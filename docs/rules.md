# 规则核对结果

**这份文档回答一个问题：仿真器实现的规则，和我实际玩的斗地主是不是同一套。**

结论如果是否定的，整个方案的地基就不成立——模型学的是这套规则，喂进去的局面按另一套规则理解，建议就没有意义。

核对日期：2026-10-31

## 怎么核对的

不是读文档，是**直接问仿真器**：构造特定的手牌，让它给出"这手牌能出什么"，看它认不认。

两个入口：

- `DoudizhuJudger.playable_cards_from_hand(hand)` —— 自由领出时，一手牌的全部合法组合
- `get_gt_cards(player, greater_player)` —— 上家出了某手牌之后，我能拿什么去压

后者通常需要完整对局对象，但实现上只用到 `current_hand` 和 `played_cards` 两个属性，

所以可以用极简的替身对象直接调用，不必真的开一局。这两条路径的探针都在
`tests/test_rules.py`，共 20 条断言。

## 四条规则的结论

| # | 规则 | 仿真器的行为 | 结论 |
|---|---|---|---|
| 1 | 顺子最少 5 张 | `3456` 不合法；`34567` 合法 | **一致** |
| 2 | 连对最少 3 对 | `3344` 不合法；`334455` 合法 | **一致** |
| 3 | 飞机带翅膀的张数 | 翅膀数必须等于三张组数：`3334445` 不合法，`33344455`、`3334445566` 合法 | **一致** |
| 4 | 炸弹与火箭的压制 | 炸弹压一切非炸弹；低炸弹压不过高炸弹；火箭压一切；火箭无解 | **一致** |

补充确认的细节：

- **2 与大小王不能入顺、也不能入连对**：`JQKA2`、`23456`、`KKAA22` 均不合法。
- **A 可以收尾顺子**：`TJQKA` 合法。
- **飞机的翅膀可以是单张，也可以是对子**，数量规则相同（几组三张配几个翅膀）。
- **连续三张可以更长**：3 组、4 组（`333444555`、`333444555666`）都合法。
- **火箭无解**：手里同时有炸弹和火箭时，面对火箭，除 pass 外没有任何合法应对。

## 第二条验收标准的核对结果：字面上不成立，但那不是问题

原验收标准写的是「验证仿真器默认交给 AI 的状态**不包含**这些真实手牌」。

字面上**不成立**：`raw_obs["others_hand"]` 精确等于另两家真实手牌的并集，同一份信息还以编码形态出现在 `state["obs"][54:108]`。

但**「并集」本来就不是秘密**——它是牌的守恒推出来的公开量：

```
每张牌只可能在三个地方：我手上 / 别人手上 / 已出的牌堆里
⇒ 另两家并集 = 全牌 − 我的手 − 已出的牌
```

任何会数牌的牌手都能算出这个集合。所以这个字段**相对于公开信息的信息量是零**，它不是泄漏。

> ### 一处已纠正的判断
>
> 本文档的上一版把这里写成了「信息泄漏」，并据此提出「推断模块禁止读该字段」。
> **那个结论是错的。** 我把「等于隐藏状态的某个函数」误当成了「泄露隐藏信息」。
>
> 隐藏的是**分配**（哪张牌在谁手上），而并集只是**待分配的牌池**——它是问题的
> 输入，不是答案。测试与文档均已改正。

### 编码观测的布局

顺带把 `state["obs"]` 的布局测清楚了。它**全部由公开或我方信息构成**，没有隐藏信息：

| 区间 | 含义 | 性质 |
|---|---|---|
| `[0:54]` | 我方手牌 | 我方信息 |
| `[54:108]` | 另两家手牌的**并集** | 公开（可推导） |
| `[108:162]` | 上一手牌 | 公开 |
| `[162:648]` | 最近 9 手 | 公开 |
| `[648:756]` | 两家已出的牌 | 公开 |
| `[756:790]` | 两家剩余张数 | 公开 |

### 各字段的实际性质

| 字段 | 性质 | 判定 |
|---|---|---|
| `current_hand` | 我自己的手牌 | 我方信息 |
| `others_hand` | 另两家手牌的**并集** | **公开（可推导）** |
| `seen_cards` | 三张底牌 | 公开 |
| `played_cards` | 各家已出的牌 | 公开 |
| `num_cards_left` | 各家剩余张数 | 公开 |
| `trace` | 出牌历史 | 公开 |
| `actions` | 我的合法动作 | 我方信息（规则推出） |
| `landlord` / `self` | 身份标识 | 公开 |

## 对方案的影响

### 一、推断问题依然成立，而且良定义

- **已知**：待分配的牌池（公开可推导）、各家剩余张数（公开）
- **要求**：把牌池在两家之间**分配**

牌池已知并不降低难度，它只是把问题从「牌池是什么 + 怎么分」收窄成「怎么分」——而后者本来就是这个项目的全部内容。

### 二、DouZero 的那个特征可以直接算，不必等推断

DouZero 的 `other_hand_cards` 特征就是上面那个并集。既然它是公开可推导的，**在真实牌局里也能直接算出来**，不需要先做出推断模块。

这一点同样纠正了上一版：当时说「推断是接入模型的前置条件」，**错了**。推断仍是项目主线，但它是独立的价值，不是模型的前置条件。

### 三、牌池由我们自己推导，不依赖仿真器的便利字段

`raw_obs["others_hand"]` 用起来很方便，但**真实牌局录入那条路径没有它**。所以统一在记录层自己算：

```
pool = 全牌 − 我方手牌 − 所有已出的牌
```

这样仿真路径与真实路径走完全相同的逻辑，也符合架构文档里「输入源可替换」的约定。理由是**可移植性**，不是保密。

## 还需要你本人确认的一件事

上面核对的是「仿真器的规则」，不是「你玩的平台的规则」——后者我无法替你验证。

这四条是各平台差异最集中的地方，建议你拿自己常玩的那个平台对一遍，尤其是**飞机带翅膀的张数**：

1. 顺子最少 5 张？四张连号能不能出？
2. 连对最少 3 对？两对能不能出？
3. 飞机带翅膀：两组三张是带 2 个单张还是可以带 1 个？能不能带对子？
4. 炸弹/火箭的压制关系有没有例外（比如某些玩法里炸弹不算翻倍）？

四条里只要有一条和你常玩的平台不一致，就要在这里记下来并重新评估方案——因为模型学的是仿真器这套规则。
